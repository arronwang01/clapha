# Clash Royale 160402012 (arm64) — every field we can read, and what we cannot

Host: MuMu Player Pro on macOS (Apple Silicon), rooted adbd, read-only via `/proc/<pid>/mem`.
`libg.so` SHA-256 `aec6cc5e473edc809f10c157ae553dbbb8724d816f34148344b7f94a67e5a97c`.

**Pointer tagging:** Android heap pointers carry a top-byte tag (e.g. `0xb4...`).
Mask every pointer with `0x00FFFFFFFFFFFFFF` before reading, or every read fails.
This is the single thing that made upstream's tooling appear broken on this host.

## Chain

```
libg_base + 0x1A57E88   -> root (manager)      # upstream 002 used 0x1A569A8
root      + 0x28        -> context
context   + 0x90        -> battle
battle    + 0xA8        -> world (player state)
world     + 0xE0 / 0xE8 -> player0 / player1
```
An alternate path `libg_base + 0x1A918B8` then `+0xC8` reaches the same battle object.

## battle

| offset | meaning | status |
| --- | --- | --- |
| `+0x60` | simulated tick, 20/s | verified |
| `+0x64` | newest tick received from server | verified (gap 6–19 ticks, median ~13.5) |
| `+0x38` | command queue vector (`+0x08` data, `+0x14` count) | verified |
| `+0x1BC` | applied replay tick | upstream field, untested here |
| `+0x30` | reads 5 | unknown |
| `+0x68` | reads 1000 | unknown |
| `+0x70` | mirrors the tick | unknown |
| `+0x74` | reads 544 | unknown |

### command queue entry

| offset | meaning |
| --- | --- |
| `+0x10` | tick the command was issued |
| `+0x18` | issuing account id, low 32 bits (`-1` for a bot/trainer) |
| `+0x28` / `+0x2c` | x / y in native units |
| `+0x38` | card LogicData pointer; card id at `+0x40` inside it |
| `+0x50` | sequence number (`-1` for a bot/trainer) |

Commands sit here ~7–12 samples (0.6–1.0 s) before the unit exists. Do not filter on `+0x04`.

## player

| offset | meaning | own | opponent |
| --- | --- | --- | --- |
| `+0x78` | side (0/1) | yes | yes |
| `+0x210` | hand vector (`+0x218` cap, `+0x21c` len), 4 deck slots 0–7 | **yes** | array exists, reads `[-1,-1,-1,-1]` |
| `+0x220` | cycle vector, same layout; next card = `cycle[0]` | **yes** | **pointer null** |
| `+0x288`..`+0x2a4` | revealed cards, card ids, first-play order, `-1` unused | **yes** | **yes** |
| `+0x2f8` | elixir × 10000 (max 100000) | **yes** | **yes, exact** |
| `+0x10` | context (→ `+0x98` player root) | yes | yes |

### deck (via player root)

```
player_root + 0x30 + i*8 -> avatar[i]   ; avatar+0x00/+0x04 = account hi/lo
player_root + 0x60       -> avatar count
player_root + 0x88 + i*8 -> owner[i]    ; owner+0x20 entries, owner+0x2c count (8)
entries[k] -> entry ; entry+0x10 -> data ; data+0x40 = card id ; entry+0x1c = form flag
```
Own owner slot resolves all 8 cards. The opponent's owner slot exists with count 8, but every
`entries[k]` pointer is **null**.

## entities

Registry gives an array of objects. Per object:

| offset | meaning |
| --- | --- |
| `+0x08` | category (native object id; towers are 5000000–5000005) |
| `+0x18` | components (hp at `+0x10` then `+0x10`) |
| `+0x30` | kind (12 king tower, 13 princess tower, 15 unit) |
| `+0x78` | side |
| `+0x7c` / `+0x80` | x / y |
| `+0xac` | card id (`-1` for towers) |
| `+0x11c` | behaviour state |
| `+0x120` | level (zero-based) |

Units carry hp and max_hp. A destroyed tower disappears from the list.

## units and conventions

- x 0–18000, y 0–32000; 1 tile = 1000; 18 × 32 grid.
- tick 20/s. Towers: king (9000,3000)/(9000,29000), princess (3500,6500)/(14500,6500)/(3500,25500)/(14500,25500).
- card id = table × 1,000,000 + row. 26 troop, 27 building, 28 spell.
- Hand/cycle hold deck slot indices, not card ids.
- Screen: canonical x mirrors for **both** sides (`x_fraction = 1 - canonical_x/18000`).
  Upstream mirrors only for side 1, which is a bug; measured and fixed here.

## What we could NOT find

The opponent's **live hand** and **cycle**, and their **8-card deck** before reveal.

Method used: dump the player object (0x600 bytes) plus 0x80 bytes at every plausible pointer it
holds (one level deep), then scan the copy offline for any 4×int32 array with values 0–7, and for
any array of valid card ids. Run against both players as a control:

- own player: 38 pointers followed, hand found as leaf of `+0x210` = `[5,1,0,6]`,
  cycle found as leaf of `+0x220` = `[2,3,7,4]`
- opponent: 32 pointers followed, **no match of either kind**, cycle pointer null

Known-good on **Null's Royale 15.535.13** (a private server) at `player+0x220` hand /
`player+0x230` cycle — shifted 0x10 from this build, so a different layout, and a server that may
simply send more. The question for anyone picking this up: **is the opponent's live hand reachable
at all on the official 160402012 client, and if so from which root?**

Caveat on the negative result: the snapshot used was taken before either player had played a card,
and reaches only one level deep at 128 bytes per pointer.
